# ATLAS production operations

Use `.venv/Scripts/python.exe ops/deploy_atlas_web.py` from the ATLAS root for frontend upgrades. It runs all frontend tests, lint with zero warnings, TypeScript checks and a production build in an isolated directory. It verifies candidate routes, login JavaScript, backend health JSON and nonempty HTTPS authentication configuration on port 8014 before stopping the production frontend. Failed post-deploy health restores the previous build. One `.next-last-good` build remains available. Builds and credentials belong outside Git. These checks do not replace a signed-in OAuth acceptance test.

The Windows supervisor observes backend, frontend, the public route, the paper monitor and MT5. It recovers only the named web and tunnel tasks after three failures, with backoff and a shared five-request budget for starts and restarts, including failed requests. Tunnel recovery requires healthy local services. A deployment maintenance marker prevents recovery from racing the build swap and expires automatically. It starts a stopped Paper Monitor after three observations, with backoff and a five-start budget until a Running task produces a fresh completed-cycle heartbeat. The root Paper runner atomically writes `paper-cycle.json` beside its ledger; a recent log alone is not health evidence, since repeated connection errors also update logs. Disabled tasks require attention. A running paper task without a fresh completed cycle is reported and never stopped or restarted. It does not submit broker orders.

Deploy the root `app/monitor/atlas_mt5.py` update together with the watchdog. Until the updated runner writes `paper-cycle.json`, a legacy Running paper task is deliberately reported as `HEARTBEAT_UNAVAILABLE`, without being stopped. The supervisor writes sanitized component states to `.runtime/server/attention.json` on every observation and clears recovered components on the next healthy observation. This is a local attention record; it does not deliver email, phone or chat notifications. `ALGO_DISABLED` is acceptable for the read-only MT5 observer and is never a reason to enable broker execution.

Windows rejected changes to the elevated web/backend task settings under the remote session. Run `ops/configure_atlas_host.ps1` in an Administrator PowerShell to remove battery-related stops. The tunnel currently requires a logged-in user. The host must remain powered, connected and awake. The latest outage includes a Windows sleep event with reason Application API; changing idle timeouts cannot guarantee protection against an application or person explicitly putting the host to sleep.

Google OAuth was verified end-to-end on 2026-10-08: the Google button returned to the dashboard and the backend /api/me resolved the authenticated account. The paper monitor was restarted after a stopped task was found; its task is Running and its paper log and ledger updated afterward. The cause of that earlier stop is not yet established. Never commit provider secrets, tunnel tokens, runtime env files or user databases. An enabled login button or HTTP 200 is not evidence of successful OAuth.

Public health probes must identify themselves as `ATLAS-Windows-Monitor/1.0`, as the production supervisor already does. On 2026-10-08 the default Python urllib client received Cloudflare error 1010, while the ATLAS monitor client returned 200 for login, dashboard and backend health. The authenticated browser dashboard also showed backend connected and rendered candles. No Cloudflare security settings were changed.
